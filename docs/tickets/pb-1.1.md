## Goal

Bootstrap the repository so that every service is a fully independent, buildable unit — as if each lived in its own repository. This ticket delivers a Docker Compose stack with Postgres and four independent Gradle projects: three Spring Boot services (`matching-engine`, `rider-api`, `driver-api`) and one plain Java simulator. **No business logic anywhere** — just runnable, independently buildable shells.

---

## Context and constraints

- **No host JDK** — each service must build and test inside Docker via its own Gradle Wrapper.
- **Java 25** — enforced by each service's own Gradle toolchain configuration.
- **Microservice independence** — each service has its own `gradlew`, `settings.gradle.kts`, and `build.gradle.kts`. You can `cd` into any service directory and run `./gradlew build` without depending on a parent project.
- **Docker-only local development** — `docker compose up` is the only command needed to run infrastructure.
- **Spring Boot 4.x** — latest stable version at project start.
- **Spring Boot Actuator** — included on all three services for health/metrics out of the box (replaces any custom health controller later).
- **Root level** — holds only shared orchestration: `docker-compose.yml`, `docs/`, `README.md`, `.gitignore`. No root Gradle build.

---

## How to obtain the Gradle Wrapper (no host install)

Since Gradle will **not** be installed on the host machine, the Wrapper files for each service are obtained by generating a project from **[Spring Initializr](https://start.spring.io)** via the browser and extracting the wrapper.

**For each Spring Boot service (`matching-engine`, `rider-api`, `driver-api`):**

1. Go to [start.spring.io](https://start.spring.io).
2. Configure:
   - **Project:** Gradle — Kotlin DSL
   - **Language:** Java
   - **Spring Boot:** 4.x (latest stable)
   - **Java:** 25
   - **Dependencies:** Spring Web, Spring Boot Actuator
3. Click **Generate** → download the `.zip`.
4. Extract and copy the following files into the service directory (e.g., `services/matching-engine/`):
   ```
   gradlew
   gradlew.bat
   gradle/wrapper/gradle-wrapper.properties
   gradle/wrapper/gradle-wrapper.jar
   ```
5. Replace the generated `build.gradle.kts` and `settings.gradle.kts` with the ones specified in this ticket (to match the correct package structure and Java 25 toolchain).

**For the `simulator` (plain Java, not Spring Boot):**

- Download one Spring Initializr zip (same settings as above) and copy only the Wrapper files (`gradlew`, `gradlew.bat`, `gradle/wrapper/`).
- Replace the generated `build.gradle.kts` with a plain Java configuration (no Spring Boot plugin).

> The Wrapper files generated by Spring Initializr are identical to what `gradle wrapper` produces locally. From this point on, everything runs inside Docker and the host machine never needs Java or Gradle.

## Acceptance criteria (done = all true)

1. Each service can be built independently:
   - `cd services/matching-engine && ./gradlew build` produces a runnable JAR.
   - `cd services/rider-api && ./gradlew build` produces a runnable JAR.
   - `cd services/driver-api && ./gradlew build` produces a runnable JAR.
   - `cd services/simulator && ./gradlew build` produces a runnable JAR.
2. `docker compose -f infra/docker-compose.yml up -d postgres` boots Postgres and the healthcheck reports `healthy`.
3. Each service image builds successfully with `docker compose build` (or `docker build` per service) with no host JDK:
   - `matching-engine` container starts and `curl http://localhost:8080/actuator/health` returns `{"status":"UP"}`.
   - `rider-api` container starts and `curl http://localhost:8081/actuator/health` returns `{"status":"UP"}`.
   - `driver-api` container starts and `curl http://localhost:8082/actuator/health` returns `{"status":"UP"}`.
   - `simulator` container runs and exits cleanly (exit code `0`).
4. The Java process inside every running container is owned by a non-root user (`puber`).
5. Runtime images (JRE stage) are noticeably smaller than the corresponding JDK build stages.
6. `docker compose down -v` removes containers and volumes cleanly.
7. No root-level Gradle files exist (no root `build.gradle.kts`, `settings.gradle.kts`, or `gradlew`).
8. No business logic files exist anywhere: zero controllers, entities, repositories, services, or domain classes.

## Explicitly out of scope for this ticket

- Flyway migrations, database schema, JDBC repositories, or domain records.
- Business endpoints (`POST /rides`, `GET /rides/{id}`, `POST /drivers/{id}/location`, etc.).
- Inter-service HTTP clients or internal endpoints (`/internal/...`).
- Kafka, Redis, WebSockets, or any message broker.
- Simulator logic: no threads, no WebClient, no random locations, no ride requests.
- Custom Actuator endpoints or Prometheus metrics.
- Cloud deployment, K8s, or CI/CD pipelines.
- Any root-level shared Gradle library or composite build setup.
