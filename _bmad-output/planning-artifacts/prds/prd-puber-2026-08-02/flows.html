Ride state machine

Four states on the happy path and three terminals. Every terminal is reachable and every one of them resolves the payment — there is no way for a ride to end and leave money in limbo.

in flight delivered terminal, no trip system-initiated recovery

Recovery reuses existing states. Neither silent-driver path needed a new state — a stalled MATCHED ride returns to REQUESTED, and a stalled IN_PROGRESS one moves to COMPLETED. The audit trail records SYSTEM as the actor, so those stay distinguishable from genuine transitions after the fact.

Payments, and when money actually moves

Two phases: the fare is authorized as a hold when the ride is requested, and captured only when a trip is delivered. Everything else releases the hold.

The rider's session

From opening the app to reading history. Every step is a capability the backend exposes — there is no screen, only the endpoint the screen would call.

  1. 01

    Check for a ride already in flight FR-4

    Looked up by rider identity, not ride id — losing the id is not a dead end. Returns at most one.

  2. 02

    Quote a trip FR-1

    Fare, distance and ETA without creating anything. Indicative only — the price is re-derived at request. With nobody online it still returns fare and distance, just no ETA.

  3. 03

    Request the ride FR-2 FR-3

    Carries a payment-method token, since no account stores one. Fare locks here. A second simultaneous request is refused.

  4. 04

    The fare is authorized before anyone is dispatched FR-9

    A declined card ends the ride at PAYMENT_FAILED without a driver ever being offered it.

  5. 05

    Watch the driver approach FR-5 FR-6

    Who is coming, where they are now, and an ETA that moves as they do. This is the line in the vision made literal.

  6. 06

    Cancel, while it is still allowed FR-16

    Only before the trip starts. Releases the driver, withdraws any outstanding offer, voids the hold. A mismatched identity is refused without revealing the ride exists.

  7. 07

    See what was charged FR-7

    Final fare and payment outcome — captured, failed or refunded — so the payment machine has a visible consequence.

  8. 08

    Read history FR-8

    Most recent first, bounded by a result limit.

The driver's session

A driver owns their own availability and can only ever act on the ride assigned to them.

  1. 01

    Read the whole working state in one call FR-21

    Declared status, whether the system can currently hear them, any offer awaiting an answer with its pickup, dropoff, fare and distance, plus the active ride if one is running.

  2. 02

    Go online FR-20

    Both directions are explicit taps — the system never puts a driver online for them. Going offline is blocked mid-ride, and releases a pending offer rather than leaving it dangling.

  3. 03

    Report position on a heartbeat FR-26

    Feeds matching, the rider's live view, and — mirrored to the columnar store — the distance and density analytics.

  4. 04

    Receive an offer, and everything else that matters FR-44

    The push channel carries offers plus the events a driver must react to: the rider cancelled, the offer was withdrawn, the ride was auto-completed.

  5. 05

    Accept — or decline FR-22 FR-23

    Declining hands the ride straight to the next-nearest driver instead of making the rider wait out the timeout.

  6. 06

    Start the trip, then complete it FR-24

    Each valid only from the preceding state and only on their own ride. Completing returns them to AVAILABLE.

  7. 07

    Review completed rides FR-25

    The driver-side counterpart to the rider's history.

Still open, by design

One question sits in the PRD. The rest are mechanism decisions parked for the architecture pass — deliberately left unfixed rather than guessed at.

QuestionWhy it is not answered here
How payments are excluded from the stress test Simulator flag, stubbed path, or a separate suite — a mechanism, not a product choice
Transport for the rider's live driver position The push channel is driver-only; rider polling versus a second channel is architecture
Three separate staleness windows Cost of a false positive rises steeply — an idle driver self-heals, a live trip ended wrongly does not
The monotonic versus wall-clock boundary Monotonic is process-local, so it cannot span the heartbeat's service boundary
How long matching waits before giving up Tune alongside the retry interval and offer timeout as one set
Authorization hold lifetime Needs the invariant: no terminal ride may hold an outstanding authorization
