- [2026-08-03] decision: [ADOPTED] Final data-ownership + dispatch model (resolves the fork above), reasoning: "if we need a saga with only 3 microservices, we're doing something wrong" (user) — chose to unify the co-written entities under one owner rather than run a saga across services, mirroring Uber's own fix at a scale where it's cheap:
  - `rider-service`: stateless façade, no database of its own. All ride reads/writes proxy to `matching-service`'s API.
  - `driver-service`: owns driver identity + location ONLY — `drivers(id, name, current_lat, current_lng, ...)`. No dispatch/status field.
  - `matching-service`: owns `rides` AND a `drivers` table of its own (renamed from working name `driver_dispatch`) holding ONLY dispatch state: `drivers(driver_id, status[OFFLINE|AVAILABLE|OFFERED|ACCEPTED_RIDE|IN_RIDE], current_ride_id, updated_at)`. Two tables named `drivers` in two separate service databases — normal under DB-per-service, not a conflict, never queried across.
  - Rule this establishes: whatever is co-written by a single action must share one transactional owner. matching-service's own scheduler/API handlers do the offer/accept/complete/timeout transitions as single local Postgres transactions across its own `rides` + `drivers` tables — no saga, no compensating action, no cross-service coordination for the write itself. The only cross-service calls are the two natural entry points (rider-service→matching-service to create a ride; driver-service→matching-service to relay a driver's accept/complete action), each triggering exactly one downstream commit — ordinary retry-on-failure, not a multi-step transaction.
  - Prevents: a future builder re-introducing a saga/compensating-action pattern for the core dispatch path, or splitting rides/dispatch-status across services again.

- [2026-08-04] event: User new to Kafka (background in SNS/SQS/RabbitMQ where ACK removes the message) — walked through how Kafka's model differs: consumption never deletes (retention is time/size-based, uniform per-topic, independent of who's read it); fan-out across independent consumer groups is the built-in default (no SNS-style multi-queue fan-out needed — this is exactly why matching-service's Redis-consumer and audit-service's ClickHouse-consumer can both read `driver.locations` independently); a late-joining consumer group only sees whatever's still inside the retention window, not full history, per its `auto.offset.reset` policy (earliest vs. latest); ordering is guaranteed only within a partition, so producers must key by entity id (driver_id, ride_id) to keep per-entity event order under multi-partition throughput; delivery is at-least-once, so every consumer must be idempotent/dedupe by event id, not just payment-service's webhook handling.
- [2026-08-04] event: Discussed why Kafka doesn't delete on ACK (user's SNS/SQS/RabbitMQ background prompted this) — clarified it's not about dedup (Kafka is at-least-once too), it's (a) fan-out to consumer groups that don't exist yet at publish time — the exact audit-service-added-in-Month-6 case, which a delete-on-ACK queue would make structurally impossible, (b) replay/reprocessing (rewind a consumer's offset, backfill a new one from the retention window), (c) performance — append-only + bulk segment deletion vs. per-message delivery-state tracking, load-bearing for the 10k writes/sec stress target.
- [2026-08-04] decision: [ADOPTED] Kafka rules, confirmed by user: (a) all Kafka producers partition-key by the relevant entity id (driver_id for driver.locations, ride_id for ride.* events, etc.) so per-entity ordering survives multi-partition throughput; (b) all Kafka consumers are idempotent/dedupe by event id — a system-wide rule, not just payment-service's webhook handling; (c) new/late-joining consumer groups (e.g. audit-service's Month-6 ClickHouse consumer) default to `auto.offset.reset=earliest`, backfilling whatever's still in the retention window rather than skipping to latest.

- [2026-08-07] decision: [ADOPTED] FR-3 one-active-ride guard is enforced by a **Postgres partial unique index**, not application-level check-then-insert (which has a TOCTOU race) and not `SELECT ... FOR UPDATE` (impossible — there is no `riders` table, so no row to lock): `CREATE UNIQUE INDEX idx_one_active_ride ON rides (rider_id) WHERE status IN ('REQUESTED','MATCHED','IN_PROGRESS')`. Second concurrent insert fails on unique violation → 409. Same philosophy as the no-saga decision: lean on the transactional store's guarantees rather than coordinating in application code. Also subsumes the `rides(rider_id, status)` index puber.md had deferred to week 14½ — same index, enforcing rather than merely accelerating.
  - User challenged this on index-maintenance latency and index growth under load testing. Analysis: SIZE is a non-issue — a partial index holds only rows matching the predicate, i.e. only *currently active* rides (terminal rides leave it automatically), so it's bounded by concurrent active rides, not total rides ever. ~40 bytes/entry ⇒ ~8 MB at the absolute worst case of all 200k stress riders active simultaneously; realistically ~600 KB. A non-partial `rides(rider_id)` index would instead grow unbounded with every ride ever created. MAINTENANCE is a real but small cost: Postgres HOT (heap-only tuple) updates skip index maintenance when no indexed column changes, but **columns in a partial index's predicate count as indexed**, so referencing `status` makes every ride transition a non-HOT update. ~3-4 transitions/ride × microseconds of cached btree work; immaterial at this scale, and the MVCC dead-tuple churn it implies exists for status updates regardless.
  - Deliberate follow-up (NOT pre-optimized): if NFR-2 stress load shows HOT breakage mattering — observable directly as `n_tup_hot_upd` vs `n_tup_upd` in `pg_stat_user_tables` — migrate the constraint to a dedicated `active_rides(rider_id PK, ride_id)` table written in matching-service's same local transaction, which restores HOT on `rides`. Chosen as a measure-then-migrate path because it also generates the kind of evidenced migration narrative the project exists to produce.

- [2026-08-11] decision: [ADOPTED] Outbox id is a **monotonic sequence (`GENERATED ALWAYS AS IDENTITY`, 8-byte bigint)**, not a UUID and not ordered by `occurred_at`. User questioned both alternatives.
  - vs UUID: the outbox needs ORDERING and random v4 UUIDs have none. The row already carries `event_id UUID` for global identity across service boundaries; `id` is a purely internal sequence number, never exposed or referenced. Also matters on this high-churn table: a monotonic key appends to the B-tree's right edge while random UUIDs scatter inserts causing page splits and poor cache locality, and 8 bytes vs 16 on every row and index entry. UUIDv7 would give both (time-ordered) but needs a Java library (`java.util.UUID` cannot generate it), a recent Postgres or `pg_uuidv7`, is still 16 bytes, and falls back to random ordering within a millisecond — not worth the dependency for an internal sequence.
  - vs `ORDER BY occurred_at`: fails three ways, all clock-related. (1) Wall-clock goes backwards on NTP correction — NFR-9 already flags this hazard for timeouts, but ordering has zero tolerance where a timeout has slack. (2) Replicas have different clocks: if one instance handles the accept and another the completion, skew can invert them — same problem as AD-18, but unabsorbable here. (3) Microsecond ties give non-deterministic order. `ORDER BY occurred_at, id` doesn't rescue it — the tiebreaker fixes ties but not backwards clocks or skew. **Principle: a sequence is monotonic because it comes from ONE authority** (all replicas of a service share one database, hence one sequence); a timestamp comes from whichever machine handled the request, and there are several. Semantic reason too: `occurred_at` answers "when did this happen in the domain", `id` answers "in what order to publish" — keeping them separate leaves room to record a backdated event without the relay reordering itself.
  - Sizing: bigint range ~9.22e18 ⇒ ~29 million years at 10k events/sec. Plain `SERIAL` (int4, ~2.1e9) would exhaust in ~2.5 days at that rate, so BIGSERIAL/identity is a correctness call, not defensive sizing. Sequence gaps from rolled-back transactions are irrelevant — the relay tracks no watermark. Chose `GENERATED ALWAYS AS IDENTITY` over `BIGSERIAL` as the current SQL-standard idiom, which also blocks accidental manual overrides on insert.
  - NOTE recorded: with a sequence, values are allocated at insert but visible at commit, so a transaction holding id=100 can commit AFTER one holding id=101 — a relay tracking a `lastSeen` watermark would skip 100 permanently. The delete-on-publish design sidesteps this entirely because it uses no watermark; late-arriving rows are simply picked up next poll.

- [2026-08-11] decision: [ADOPTED] **Per-row retry, not per-batch.** User raised that `tries` tracking was missing. Problem it fixes is worse than it looks: with plain rollback-on-failure, ONE failure rolls back the whole batch — publish 100, #47 fails, and #1-46 are undone too; next poll claims the same batch and fails identically, so a single poison event stalls the entire stream permanently.

- [2026-08-11] decision: [ADOPTED] **Backoff and circuit-breaker solve different failures and both are needed**: per-row exponential backoff (`tries`) isolates ONE poison event without touching healthy traffic; a relay-level circuit breaker (Resilience4j, already in the stack for FR-32/NFR-3) handles the downstream being entirely down. - [2026-08-11] decision: [ADOPTED — user's refinement] **The breaker is checked BEFORE claiming rows from the database**, not after. Makes the rule above *structurally impossible to violate* rather than a discipline to remember: rows never fetched cannot have their `tries` incremented.
