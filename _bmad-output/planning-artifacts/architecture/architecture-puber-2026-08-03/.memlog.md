- [2026-08-03] event: User referenced Uber's fulfillment-platform rearchitecture article (docs/uber.md) — old Uber architecture (rt-demand/Trip + rt-supply/Supply, one entity each) hit exactly this cross-entity-write problem and used a Saga (propose/commit/cancel) to coordinate; they explicitly called this out as painful to debug and inconsistent mid-transaction. New Uber architecture eliminated the saga by unifying the transactional boundary (Spanner, cross-table ACID transactions) rather than adding more saga machinery. Uber's "statecharts" (explicit hierarchical state machine per entity: states/transitions/triggers) flagged as a good low-cost pattern to borrow regardless of the storage decision.
- [2026-08-03] decision: [ADOPTED] Final data-ownership + dispatch model (resolves the fork above), reasoning: "if we need a saga with only 3 microservices, we're doing something wrong" (user) — chose to unify the co-written entities under one owner rather than run a saga across services, mirroring Uber's own fix at a scale where it's cheap:
  - `rider-api`: stateless façade, no database of its own. All ride reads/writes proxy to `matching-engine`'s API.
  - `driver-api`: owns driver identity + location ONLY — `drivers(id, name, current_lat, current_lng, ...)`. No dispatch/status field.
  - `matching-engine`: owns `rides` AND a `drivers` table of its own (renamed from working name `driver_dispatch`) holding ONLY dispatch state: `drivers(driver_id, status[OFFLINE|AVAILABLE|OFFERED|ACCEPTED_RIDE|IN_RIDE], current_ride_id, updated_at)`. Two tables named `drivers` in two separate service databases — normal under DB-per-service, not a conflict, never queried across.
  - Rule this establishes: whatever is co-written by a single action must share one transactional owner. matching-engine's own scheduler/API handlers do the offer/accept/complete/timeout transitions as single local Postgres transactions across its own `rides` + `drivers` tables — no saga, no compensating action, no cross-service coordination for the write itself. The only cross-service calls are the two natural entry points (rider-api→matching-engine to create a ride; driver-api→matching-engine to relay a driver's accept/complete action), each triggering exactly one downstream commit — ordinary retry-on-failure, not a multi-step transaction.
  - Prevents: a future builder re-introducing a saga/compensating-action pattern for the core dispatch path, or splitting rides/dispatch-status across services again.
- [2026-08-03] decision: [ADOPTED] Driver location — two eras, re-homed under the new ownership:
  - V1 (pre-Kafka, fixture scale ~30 drivers): driver-api writes its own `current_lat/lng` on heartbeat, then synchronously calls matching-engine's internal API to update its own cache (in-memory or extra columns on its `drivers` row). Never needs to survive stress scale — Kafka lands (Month 3+) before the NFR-2 stress test (late-phase milestone), so this shortcut is retired before it would need to scale.
  - Month 3+ (Kafka): driver-api produces `driver.locations` event AND writes its own durable `driver_locations` history table directly (its own DB, no cross-service concern). matching-engine's own consumer of that event writes the latest position to **Redis** (`SETEX driver:{id}:location 60s ...`) — matching-engine's matching queries read ONLY Redis, never Postgres, for live location once Kafka exists.
  - Reasoning: Redis fits latest-value-only, extremely high-write-rate data (~10k writes/sec at 20k-driver stress scale) with no durability need (fully re-populates within one heartbeat cycle) and natural TTL-based staleness handling.
