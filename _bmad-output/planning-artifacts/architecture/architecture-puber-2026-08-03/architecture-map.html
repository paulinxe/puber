Service topology

Five services behind one gateway. The rule that shapes everything else: matching-service is never publicly routable. It holds all authoritative ride and dispatch state, and reaching it only through the edge services is what makes the façade layer mean something.

on the hot path event backbone boundary rule

Internal hops bypass the gateway. rider-service → matching-service and driver-service → matching-service resolve through Docker DNS in Compose and through a Kubernetes Service later — each of which load-balances on its own. HAProxy is the edge and nothing else, so there is no second load-balancer component to run.

Who owns what

Database per service. The rule that decides where a table lives: whatever is written together by a single action must share one transactional owner. That is what removes the need for a saga anywhere in the core dispatch path.

ServiceOwnsNotes
rider-service nothing Stateless façade. Every read and write proxies to matching-service.
driver-service drivers — id, name, current position Identity and location only. Carries no dispatch status.
matching-service rides, drivers (dispatch), fare_rules A second table also called drivers — different database, different purpose, never joined across. Holds only driver_id · status · current_ride_id · updated_at.
payment-service payment_intents, webhook_events The only service that talks to Stripe.
audit-service audit_events + ClickHouse tables Also ingests driver.locations into its own ClickHouse table for FR-43.

Authoritative vs advisory

FactAuthoritativeAdvisory copyWhy safe
Is this driver free? matching-service drivers.status drivers:geo membership Conditional UPDATE … WHERE status='AVAILABLE' decides; loser re-searches
Where is this driver? nowhere durable — it is ephemeral driver:{id}:position Staleness only affects match quality, never correctness
Who is the driver? driver-service drivers snapshot on the ride row Snapshot is more correct — records who actually drove it

Never trust a cache for correctness — only for candidate selection. This one sentence covers the driver-location cache, the geo set, and the identity snapshot. It is also what makes Redis read-replicas safe to add later without changing any logic.

Ride lifecycle

Five states on the happy path, three terminals. REQUESTED means awaiting authorisation and nothing else — it is entered exactly once and never returned to, so a ride that already holds funds can never fall back into re-authorising them.

in flight delivered terminal, no trip system recovery

Provenance is a field, not a state. An auto-completed ride ends in COMPLETED like any other, with completed_by = DRIVER | SYSTEM alongside it. A separate AUTO_COMPLETED status would force every "completed rides" query — rider history, driver history, analytics, the capture trigger, dashboard counts — to match two values, and missing one gives a silent bug.

The ride state cannot tell an offer from an acceptance. MATCHED covers both "offered, awaiting an answer" and "accepted, driving to pickup". That distinction lives in matching-service's dispatch enum (OFFERED vs ACCEPTED_RIDE) — without it, the offer-timeout sweep has nothing to filter on.

The two flows that shape everything

One is the highest-value path, the other the highest-volume one.

Requesting a ride

  1. 01

    Quote — no ride created

    Fare from fare_rules plus an ETA from the nearest matchable driver. Indicative only, so it can be served from a coarse per-cell cache if GEOSEARCH load bites.

  2. 02

    Request — persisted immediately as REQUESTED

    The ride id comes straight back. A partial unique index enforces one active ride per rider; a concurrent second request fails on the constraint and becomes a 409.

  3. 03

    Authorise — asynchronously

    The payment token passes through to payment-service as a typed value that cannot be logged. Nothing blocks on Stripe.

  4. 04

    Hold lands → WAITING_MATCH

    Matching reads only this state, so an unfunded ride is invisible to dispatch rather than merely rejected by a guard. A decline goes to PAYMENT_FAILED instead.

  5. 05

    Match — one local transaction

    GEOSEARCH picks a candidate; the conditional update on the dispatch row decides. Ride and dispatch state are written together, in one database, with no cross-service coordination.

The driver heartbeat — 10k writes/sec at stress scale

  1. 01

    driver-service receives the heartbeat, stamps it

    Stamped at produce time. Stamping on consume would let Kafka lag mask staleness — a backed-up consumer makes every vanished driver look freshly heard, and it fails worst under load.

  2. 02

    Published to driver.locations

    Keyed by driver_id, so one driver's events stay ordered relative to each other across partitions.

  3. 03

    matching-service writes Redis — two ops, one round trip

    GEOADD drivers:geo and the position hash. Zero Postgres writes: a last_heartbeat_at column would mean 10k updates/sec on a hot row.

  4. 04

    audit-service consumes the same topic independently

    Into ClickHouse for the FR-43 analytics. Two consumer groups on one topic, neither aware of the other — the thing a delete-on-ack queue could not do.

How the code is organised

Layered packaging with the Strategy pattern for the pieces that vary — deliberately not hexagonal. The general trend favours package-by-feature, but that argument doesn't apply here: the feature decomposition already happened at the service boundary. The package is called a service.

Every service

com.puber.{service}
  controller/   entrypoints
  service/      orchestration + logic
  repository/   JdbcTemplate, explicit SQL
  model/        records + state machines
  strategy/     the swappable bits
    payment/  location/  events/
  config/

model/, not entity/ — the latter reads as JPA @Entity, and there is no ORM here. A name that implies one invites someone to reach for Hibernate.

matching-service only

com.puber.matching
  shared/     Location, haversine
  fare/       rules, calculation, surge
  ride/       model, state machine, lifecycle
  dispatch/   geo index, matching, offers
  quote/      fare + nearest driver
  config/

shared ← fare ← ride ← dispatch ← quote

The only service carrying more than one domain, so the only one split by feature. Flat inside each package, petclinic-style.

The invariant is dependency direction, not folder names. model/ imports nothing framework-flavoured; service/ imports model/ and strategy interfaces, never a concrete implementation; nothing imports controller/. The moment a service class imports StripePaymentProvider instead of PaymentProvider, the stub stops being swappable and AD-27 quietly breaks.

Two placements in matching-service exist to prevent cycles. The match transaction writes both rides and drivers, so it lives in dispatch/ and calls down into ride/. Surge needs counts from both, so its scheduler also lives in dispatch/ and writes the multiplier down into fare/ — put it in fare/ and the whole order collapses.

One place a port must not go: Postgres. NFR-1's race-safety guarantee is the database's behaviour — row locks, the partial unique index, conditional updates. A fake repository has none of those semantics, so tests against it would pass while the real system double-books drivers. Testcontainers against real Postgres instead. A strategy where the implementation varies; direct access where the technology's semantics are the thing being relied on.

Events

Domain code never publishes. It writes a row in the same transaction as the state change, and a relay ships it. That makes publishing fire-and-forget by construction — so the V1-HTTP → Kafka migration swaps one class and touches nothing else.

The relay loop

  1. 01

    Check the circuit breaker before touching the database

    Rows never fetched can't have their tries incremented — so "an outage must not burn retry budget" becomes structurally impossible rather than a rule to remember. Use tryAcquirePermission(), not getState(), or half-open probing is lost.

  2. 02

    Claim a batch with FOR UPDATE SKIP LOCKED

    Load-bearing, not decoration: replicas would otherwise claim the same rows and publish duplicates. Shrink the batch to one or two while half-open — probing with a hundred costs a hundred failures if the downstream is still broken.

  3. 03

    Publish each, then resolve per row

    Success deletes the row; failure increments tries and pushes next_attempt_at out by exponential backoff. Per row, not per batch — otherwise one poison event rolls back its ninety-nine healthy neighbours and the stream stalls forever.

  4. 04

    At the cap, stamp dead_at and stop

    No separate table — the partial index keeps dead rows out of every future claim. Revival is a manual UPDATE; the metric is what tells you to go look.

Backoff and the breaker solve different failures. Per-row backoff isolates one bad event without touching healthy traffic. The breaker handles the downstream being gone. Without the breaker, an outage makes every row burn retries and inflate its backoff, so recovery is slow and lumpy — and breaker rejections must never count as tries, or a two-minute blip mass-dead-letters the entire outbox.

The outbox is itself a bounded queue. Kafka down with Postgres up means rows accumulate unchecked — the exact failure AD-6 exists to prevent, in a queue we created and then left unbounded. Past the bound, new ride requests are shed with a 503. Trigger on age, not depth: a large backlog draining healthily is fine, a small one that hasn't moved in ten minutes is broken.

The envelope, and what belongs in it

The envelope carries what transport and cross-cutting consumers need to route, deduplicate and record. The body carries what the domain means. Anything infrastructure must read to do its job gets promoted to a column, so it never parses the payload — which is why entity_id is a column rather than dug out of JSON, and why actor sits in the envelope: audit-service reads it uniformly for every event type.

RuleWhy
Payload is the built event, as JSONB Building it at publish time reads state seconds later — a ride.matched could ship carrying IN_PROGRESS, describing a transition that never happened
Never native serialisation Consumers are independently built with duplicated domain code; a serialised Java object would force the shared library the project rejected
Fat events, but bounded to a contract Thin events would make audit-service call back per event — a callback storm, and it would record state as of the callback rather than the transition
Evolve by addition only Same expand-only discipline as the Flyway migrations. Breaking changes get a new event_type, never a mutated one
Consumers ignore unknown fields Without it additive-only collapses. Spring Boot's ObjectMapper does this; a hand-built one in Kafka config does not — the unsafe path is the default exactly where it matters
Heartbeats never use the outbox 10k writes/sec through a Postgres table is the hot-row pattern we moved to Redis to escape. Location pings are telemetry, not state transitions

What each store is for — and is not

StoreHoldsExplicitly not
Postgres per service Every authoritative fact. One instance per service, never shared. Live driver positions — that write rate would sit on a hot row.
Redis Latest driver position and the matchable geo index. Month 3+. A source of truth for anything. Not durable, not history, not surge.
Kafka The event backbone and the only durable record of the location stream. A queue. Nothing is deleted on acknowledgement — retention is time-based.
ClickHouse Audit history and the location-derived analytics of FR-43. Anything on a request path. Analytical reads only.

There is no durable location history in Postgres. Location pings go Kafka → ClickHouse and nowhere else. A row store would be carrying roughly 10k inserts/sec for data whose only consumer is aggregate analytics.

API conventions

Small rules, but the kind two independently-built services diverge on within a week of each other.

ConventionRulePrevents
Split by volatility GET /rides/{id} for slow-changing detail; GET /rides/{id}/driver-position for position + ETA One volatile field making the whole resource uncacheable
Conditional GET ETag + If-None-Match on ride detail — 304 on the common path A TTL cache serving a stale ride status
Sub-resource addressing Rider-scoped data hangs off the ride, never off the driver Driver identifiers appearing in rider-facing URLs at all
404, never 403 Identity mismatch is indistinguishable from a ride that does not exist A 403 confirming the resource exists
Internal ids stay internal Ride detail returns the driver's name, not their UUID Internal identifiers leaking across an actor boundary

None of this is a security boundary. Identity is passed per-request and trusted as-is (FR-47), so anyone can send a different rider identifier. These are correct shapes, practised so the habit exists — the same framing as the payment-token discipline. Size the effort accordingly.

Redis

Arrives in Month 3 with the Kafka phase. Months 1–2 have none: thirty drivers is a linear scan, and a geo index at that size is ceremony.

Configuration

TopologyOne instance. No cluster, no replicas.
No clusterNot "not yet" — it would not help. Cluster shards by key, and drivers:geo is one key.
No replicasThis one is "not yet". Add when the stress run says so.
PersistenceOff. Every value rebuilds within one heartbeat cycle, so durability buys nothing and costs fork pauses on the hottest path.
Memory≈5 MB at 20k drivers. noeviction, so growth is loud rather than silent.

Keys

drivers:geo Matchable drivers only. At stress scale most drivers are busy, so a set holding everyone would return mostly-ineligible candidates.
driver:{id}
:position		 Every driver, TTL'd. The rider needs the position of a driver on their ride — precisely one excluded from the matchable set.

Stale members are cleaned lazily: a GEOSEARCH hit whose position key has expired is ZREM'd on the spot. An eager sweep is deferred until ghosts prove to matter.

When it saturates — in this order

  1. Pipeline the matching sweep.It already batches rides; batching the GEOSEARCHes removes the network round-trip that dominates throughput. Often several× for free.
  2. Serve quote ETAs from a coarse cache.Quotes are indicative by definition and already tolerate returning no ETA. This removes the largest and least valuable source of GEOSEARCH load.
  3. Add read replicas.Safe precisely because the geo set is advisory — a lagging replica's stale candidate is rejected by the authoritative conditional update.
  4. Partition geo keys by cell.The only thing that makes Redis Cluster useful here. Cells must be substantially larger than the search radius or boundary queries eat the gain.

Do not pre-solve this. NFR-2 exists to surface exactly these bottlenecks, and the single-hot-key limit is far more memorable discovered than designed around. Instrument ops/sec, p99 latency and INFO commandstats from day one, and let the stress run decide.
