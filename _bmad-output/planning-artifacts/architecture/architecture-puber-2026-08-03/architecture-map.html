Service topology

Five services behind one gateway, and one rule shaping everything else: matching-service is never publicly routable. It holds all authoritative ride and dispatch state, and reaching it only through the edge is what makes the façade layer mean something rather than being an optional hop.

on the hot path event backbone boundary rule

Kafka never removes the synchronous path. The façades own no data, so a rider's request must reach matching-service to get back a ride id, a 409, or a read result — fire-and-forget cannot deliver any of those. Events carry propagation; anything an actor waits on stays a call. AD-37

Who owns what

Database per service. The rule deciding where a table lives: whatever is written together by a single action shares one transactional owner. That is what removes the need for a saga anywhere in the dispatch path.

Ride lifecycle

Six states on the happy path, three terminals. REQUESTED means awaiting authorisation and nothing else — entered exactly once, never returned to, so a ride already holding funds can never fall back into re-authorising them.

in flight delivered terminal, no trip system recovery

OFFERED is a real state, and that simplified two other things. With the ride able to distinguish "offer outstanding" from "driver accepted", the dispatch enum collapses to OFFLINE / AVAILABLE / BUSY, and FR-6 becomes true as literally written — the rider sees a driver only once one has actually committed. AD-13

Provenance is a field, not a state. An auto-completed ride ends in COMPLETED with completed_by = SYSTEM. A separate terminal state would force every "completed rides" query to match two values, and missing one silently drops those rides from a report — or from a capture. AD-18

The two flows that shape everything

One is the highest-value path; the other is the highest-volume one.

Requesting a ride

  1. 01

    Quote — nothing created

    Fare plus an ETA from the nearest matchable driver. Indicative by definition, so it can be served from a coarse cache if geo load ever bites.

  2. 02

    Request — persisted immediately as REQUESTED

    The id returns at once. A partial unique index enforces one active ride per rider; a concurrent second request fails the constraint and becomes a 409 rather than a race.

  3. 03

    Authorise — asynchronously

    The token passes through as a typed value that cannot be logged. Nothing blocks on the provider, so provider latency never sits in the request path.

  4. 04

    Hold lands → WAITING_MATCH

    Matching reads only this state, so an unfunded ride is invisible to dispatch rather than rejected by a guard someone must remember to write.

  5. 05

    Offer — one local transaction

    A geo search picks the candidate; the conditional update on the dispatch row decides. Ride and dispatch state are written together, in one database, with no cross-service coordination.

The driver heartbeat — the system's highest-volume write

  1. 01

    driver-service stamps it at produce time

    Stamping on consume would let consumer lag mask staleness — a backed-up consumer makes every vanished driver look freshly heard, and it fails worst under load.

  2. 02

    Published keyed by driver

    So one driver's events stay ordered relative to each other across partitions.

  3. 03

    matching-service writes Redis — two ops, one round trip

    Geo set plus position key. Zero Postgres writes: a heartbeat column would mean thousands of updates per second on a hot row.

  4. 04

    audit-service consumes the same topic independently

    Its own consumer group, unaware of the other. The thing a delete-on-acknowledge queue could not do — and the reason audit can be switched off without losing anything.

How the code is organised

Layered packaging with Strategy for the parts that vary — deliberately not hexagonal. The trend favours package-by-feature, but that argument does not apply here: the feature decomposition already happened at the service boundary. The package is called a service.

Every service

com.puber.<role>
  controller/   entrypoints
  service/      orchestration + logic
  repository/   JdbcTemplate, explicit SQL
  model/        records + state machines
  strategy/     the swappable bits
  config/

model/, not entity/ — the latter reads as JPA, and there is no ORM. A name implying one invites someone to reach for Hibernate.

matching-service only

com.puber.matching
  shared/     Location, haversine
  fare/       rules, calculation, surge
  ride/       model, state machine, lifecycle
  dispatch/   geo index, matching, offers
  quote/      fare + nearest driver
  config/

shared ← fare ← ride ← dispatch ← quote

The only service carrying more than one domain, so the only one split by feature. Flat inside each package.

The invariant is dependency direction, not folder names. The moment a service class imports a concrete provider instead of its interface, the stub stops being swappable and the stress-test exclusion quietly breaks. AD-8

Two placements exist purely to prevent cycles. The match transaction writes both tables, so it lives in dispatch and calls down into ride. Surge needs counts from both, so its scheduler lives there too and writes down into fare — put it in fare and the whole order collapses. AD-9

One place a Strategy must not go: Postgres. The race-safety guarantee is the database's behaviour — row locks, partial unique indexes, conditional updates. A fake repository has none of it, so tests would pass while the real system double-books drivers. Tests run against the real stack instead. AD-10 AD-56

Events

Domain code never publishes. It writes a row in the same transaction as the state change, and a relay ships it — which makes publishing fire-and-forget by construction rather than by convention.

The relay loop

  1. 01

    Check the breaker before touching the database

    Rows never fetched cannot have their retry count incremented — so "an outage must not burn retry budget" becomes structurally impossible rather than a rule to remember.

  2. 02

    Claim a batch, skipping locked rows

    Load-bearing with replicas, which would otherwise claim the same rows and publish duplicates. Probe with a small batch while half-open.

  3. 03

    Publish each, resolve per row, commit once

    Per row, not per batch — otherwise one poison event rolls back its ninety-nine healthy neighbours and the stream stalls forever.

  4. 04

    At the cap, mark dead and stop claiming

    The partial index keeps dead rows out of every future claim. Revival is manual; the metric is what says to go look.

Two combinations that would have broken the system, caught at review. Dead rows stay in the table by design — so if the shed metric counted them, one poison event would age the backlog forever and shed every ride request permanently. The age metric counts only claimable rows. AD-35

And identity values are assigned at insert but become visible at commit — so a relay tracking a high-water mark would skip a late-committing row forever, reintroducing exactly the dual-write loss the outbox exists to prevent. The relay claims and deletes; it never remembers a cursor. AD-29

What each store is for — and is not

StoreHoldsExplicitly not
Postgres per serviceEvery authoritative fact. One instance per service, never shared.Live driver positions — that write rate belongs nowhere near a hot row.
RedisLatest position, and the matchable geo index. Owned solely by matching-service.A source of truth for anything. Not durable, not history, not surge.

Absence is never evidence of staleness. Redis holds no persistence, so after a restart every position key is gone while the drivers behind them are perfectly healthy. A sweep may act only on a recorded timestamp older than its window — reading a missing key as "stale" would auto-complete and capture every in-flight ride at once. AD-26

API conventions

Small rules, but exactly the kind five services built months apart diverge on. REST at the edge, gRPC between services, and one error vocabulary mapped at the façade.

SituationgRPCPublic HTTP
Guarded transition rejected — wrong stateFAILED_PRECONDITION409
One active ride already existsALREADY_EXISTS409
Identity mismatch, or absentNOT_FOUND404 — never 403
Lost a race; a retry may succeedABORTEDretried internally, never surfaced
MalformedINVALID_ARGUMENT400
Shed by a boundUNAVAILABLE503

That ABORTED row is a real gain over plain REST. It separates "this can never succeed" from "you lost a race, try again" — precisely the matching-worker collision where two workers pick the same nearest driver. Over HTTP both would have collapsed into an indistinguishable 409. AD-38

None of this is a security boundary. Identity is passed per request and trusted as-is, so anyone can send a different one. These are correct shapes, practised so the habit exists — the same framing as the payment-token discipline. Size the effort accordingly. AD-39

Operations

One local Kubernetes cluster is the final target — no cloud vendor at any point. Which makes the resource budget real, and makes it worth knowing in advance what can be switched off.

What can be turned off

TierComponentsIf it is off
1 — coreHAProxy, rider / driver / matching + their Postgres, Redis, KafkaSystem is down
2 — featurepayment-service + its PostgresNew rides stall before dispatch — admission control, not a crash
3 — optionalaudit-service, columnar store, Prometheus, Grafana, dashboardNothing breaks, and nothing is lost

A component can be turned off exactly when it sits behind an event boundary. Anything on the synchronous request path cannot. Tier 3 loses no data because consumer offsets survive and the backlog drains on return — the "consumption never deletes" property doing real work. The only bound is Kafka's retention window. AD-48

When Redis saturates — in this order

  1. Pipeline the matching sweep.It already batches; batching the searches removes the round-trip that dominates throughput.
  2. Serve quote ETAs from a coarse cache.Quotes are indicative by definition and already tolerate returning no ETA — the largest and least valuable source of load.
  3. Add read replicas.Safe precisely because the geo set is advisory; a lagging replica's stale candidate is rejected by the authoritative update.
  4. Partition geo keys by cell.The only thing that makes clustering useful, since a single key cannot be sharded. Cells must be substantially larger than the search radius or boundary queries eat the gain.

Do not pre-solve this. The stress test exists to surface exactly these bottlenecks, and a single-hot-key limit is far more memorable discovered than designed around. Instrument first; let the run decide.
